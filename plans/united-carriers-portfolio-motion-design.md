## 1. 作りたい体験

「アプリを作れる人の作品一覧」から、**アイデアが画面になり、動くアプリになり、使う人へ届く過程を歩けるポートフォリオ**へ発展させる。

物流サイトの船やクレーンを持ち込む必要はない。参考にするのは、スクロールで主役が動き、形を変えながら次の章へ進む構成。RH側の主役は、既存のRH、鳥のロゴ、アプリアイコン、実際のアプリ画面、コードとする。

読むための領域と、触って遊ぶ領域を明確にする。本文・フォーム・主要ナビゲーションの位置は安定させ、主にロゴ、アプリ画面、装飾の点、補助プレビューを動かす。

### PCとスマホの大きい違い

PCでは視点移動や広い余白を使える。スマホでは「まず用途が読める」「一つずつ操作できる」を優先し、Heroの重いscrubは短縮または省略する。タップをhoverの代用にしない。章の意味と素材を共通にし、操作方式を変える。

## 4. 最優先：触るとほどけるフッター文字

参照カタログG28。最も分かりやすい差分で、今の文字waveから発展させやすい。参照サイトでの**マウス入力→崩れ→復元の直接観測は未完了**。下記は配信コードの確認とRH側の要件から組み立てた設計案。

### 4.1 見せ方の決定

- 最初の実装対象は、既存の大きい`Ryuto Hara.`と同じ位置・大きさの点描ワードマーク。
- 現在の文字waveと粒子版を同時に動かさず、粒子版が使える環境では置き換える。
- 通常のブランド名・ホームリンクはHTMLで残す。粒子canvasは装飾として`aria-hidden`。
- 主に落ち着いた単色の点。最後の点、または限られた範囲へブランドの青を使う。常時虹色にはしない。
- 鳥のRHロゴを粒子化する版は第二候補。細い翼を粗い点で失わないか、単色版・大きさを比較して決める。
- HTML文字が消えた後に空白が出ないよう、canvasの初回描画完了までは現在の静止した名前を表示する。

### 4.2 体験の状態

| 状態 | 画面 | 入力・遷移 |
| --- | --- | --- |
| 未初期化 | 静止したHTMLの名前 | 表示が近づいたらfont・寸法・点を準備 |
| 静止 | 点が文字の形を作っている | マウスが影響範囲へ入るまでrAFを眠らせる |
| 接近 | 近い点だけが少し避け始める | 距離に応じた滑らかな減衰。境界で急に弾かない |
| なぞる | マウスの通り道がほどけ、点が周囲へ流れる | 遠い文字は形を保つ。名前全体を一斉に爆発させない |
| 離れる | 速度を失いながら元の文字へ戻る | 小さいゆらぎは許すが、長い振動を残さない |
| 復元 | 完全な名前として読める | 位置・速度の閾値を満たしたら描画ループを止める |
| 非表示 | 描画停止 | 復帰時は巨大な経過時間で飛ばさず、整った状態から再開 |
| タッチ／reduced motion | 静止した名前 | 触るためにタップやスクロールを奪わない |

### 4.3 粒子の作り方

1. 対象フォントの準備を待つ。待てない場合はHTML文字を維持する。
2. offscreen用の2D canvasへ、現在の表示寸法で名前を描く。
3. alphaを一定間隔でサンプリングし、文字の内側にある点だけ採用する。
4. 点ごとに原点、現在位置、速度、半径、必要なら色を保持する。
5. リサイズ・フォント変更・テーマ変更で必要な点配置だけ作り直す。
6. ポインター位置はcanvasのrectからローカルCSS座標へ変換する。DPRは描画解像度にだけ使い、物理座標と混ぜない。

外部ロゴ画像をそのまま借りず、HTMLの名前か既存の自作アセットを使う。候補は`public/brand/rh-flame-orange-blue.svg`、単色版、`rh-flame-white.svg`。

### 4.4 動きのモデル

単に点をランダムな場所へ移すと、文字に触れた感じが弱くなる。次の三つを組み合わせる。

- **復元力**：原点と現在位置の差に比例して戻す。
- **反発力**：ポインターに近いほど強く、影響半径の外ではゼロ。半径内で滑らかに変化させる。
- **減衰**：速度を少しずつ失わせ、離れた後に収束させる。

式の考え方：`加速度 = 復元力 + 反発力 - 減衰 × 速度`。時間差分を使い、60Hzと120Hzで復元時間が大きく変わらないようにする。ポインターと点の距離がゼロの場合は正規化の割り算を避ける。

| 調整項目 | RH用の試作値 | 比較する観点 |
| --- | --- | --- |
| サンプリング間隔 | 4〜6 CSS px | 文字の形と点の密度。小さい表示では間引く |
| 点の直径 | 1.5〜2.2 CSS px | 薄すぎず、面のようにつぶれないか |
| 影響半径 | 60〜100 CSS px | マウスの周囲だけがほどけるか |
| 最大変位 | 40〜90 CSS pxを目安に制限 | 名前全体が見失われないか |
| 復元の見た目 | 離れて0.6〜1.2秒程度で読める形へ | 数値は目標。実画面を見て決める |
| 粒子数 | 最初は2,000〜5,000点を目安 | 実機で安定しなければ密度を下げる。基準を満たした実測値ではない |
| DPR | 上限1.5〜2を比較 | 細部の見え方と描画コスト |

### 4.5 既存コードへの組み込み

| 対象 | 役割・変更案 |
| --- | --- |
| `src/components/Footer.tsx` | 既存の配置・ナビゲーションを維持し、大きい名前の表示器だけ差し替え可能にする |
| `src/components/FooterMotion.tsx` | 名前の登場・時計は役割を保ち、粒子表示と旧waveの同時起動を避ける |
| `src/components/Footer.css` | 現在の高さ・余白・テーマ色を使い、canvas準備中のHTML fallbackを定義 |
| 新規候補`ParticleWordmark.tsx` | 表示条件、canvas、pointer、観測、cleanupを管理 |
| 新規候補`particleWordmark.ts` | サンプリングと物理更新。Reactに依存しない計算へ分離 |
| `src/lib/pointerSpring.ts` | 現在の文字単位wave等で使用。点の独立速度を扱う処理と無理に共用しない |
| `src/components/CursorRing.tsx` | 粒子の周囲で大きいmagnetic吸着をしない。ポインターの見える位置と反発中心を一致させる |

参照コードと同じ数式・固定係数をそのまま移植する必要はない。参照コードにはframe単位の係数やDPRに依存する範囲があり、RH側では時間とCSS座標で設計し直す。

### 4.6 受け入れ条件

- [ ] なぞった部分だけがほどけ、触れていない部分は名前として残る。
- [ ] 押下せずマウス移動だけで反応する。クリックを必須にしない。
- [ ] 素早く往復しても点が消えたり画面外へ飛び続けたりしない。
- [ ] 離れた後に元の名前へ戻り、無限に振動しない。
- [ ] スクロールした後でも反発中心がカーソルと一致する。
- [ ] テーマ変更・ウィンドウ変更・戻る操作で二重canvasやlistenerが残らない。
- [ ] キーボードだけでフッターの全リンクへ到達できる。
- [ ] タッチ・reduced motion・canvas失敗時も名前と連絡導線を表示する。
- [ ] 非表示時と静止時に連続描画を続けない。

## 5. Heroから注目アプリへ、主役を受け渡す

参照H02〜H07、H11〜H24。物流の被写体の代わりに、既存の公転アイコンを次の紹介画面へ渡す。

### 5.1 推奨する一つの流れ

| 正規化した進捗 | 見せ方 | 入力との対応 |
| --- | --- | --- |
| 0〜0.2 | 見出しとRHが読める。アイコンは公転 | 入口の情報は固定した理解の基準として残す |
| 0.2〜0.5 | RHと公転全体を少し奥へ送り、最初の注目アプリを手前へ | 次に何を紹介するかを絞る |
| 0.5〜0.8 | 選んだアイコンの周囲にアプリ画面の枠が現れる | 「アイコンを開いた」感覚で画面へ接続 |
| 0.8〜1 | 紹介画面が所定位置へ収まり、見出し・主CTAが読める | 通常のProductShowcaseへ戻る |

数値はタイムラインを比較するための仮配分。巨大な固定区間を先に作らず、一画面前後の移動で意味が分かるか試す。既存の空の帯と合わせて、同じ内容のない移動区間を重ねない。

### 5.2 技術上の重要点

- 常時公転とscrub中の位置を同じstyleへ別々に書かない。外側の受け渡しwrapperと、内側の公転wrapperを分ける。
- 公転中の現在位置から受け渡すか、あらかじめ決めた位置へ集めるかを決める。初回試作では、手前へ来たアイコンに依存せず、最初の作品を明示的に選ぶ方式が安定する。
- 別DOMのアイコンを画面間で動かすなら、始点と終点のrectを一度測り、transformで補間する。毎frameの再レイアウトを避ける。
- アプリのリンクや停止ボタンのクリック領域を、見えている表示と一致させる。
- 下から戻ったときも過去の公転時刻へ不自然に飛ばないよう、演出状態と公転時刻を別管理する。
- `HeroUniverse.tsx`のcontext loss、非表示停止、fallbackを維持する。
- スマホとreduced motionでは空間の移動を省き、アイコンとアプリ画面を通常レイアウトで続ける。

### 5.3 他の案との比較

| 案 | 得られること | 問題・判断 |
| --- | --- | --- |
| RHが画面いっぱいに拡大し、文字の穴から次へ進む | 大きい見せ場、ブランドの強調 | 本文を覆う時間が増えやすい。初回・短い区間だけの比較候補 |
| アプリアイコン→実画面 | 作品を開く意味が直感的 | 第一候補。既存のアプリ群と結びつく |
| 宇宙→海→地上をそのまま再現 | 景色の変化は強い | RHの制作活動との関係が弱い。採用しない |

## 6. 注目アプリ：画面を動かして説明する

現在の`--story-progress`を使い、選択中の一作品について「全体→使う場所→結果」を見せる。タブの切り替えそのものを長い登場演出にしない。

| アプリ | 使う素材 | 3段階の説明 | 避けること |
| --- | --- | --- | --- |
| BusTimeApp | 現在のホーム画面、通知、Widget／Live Activity素材 | 次の便を確認→出発前の通知→アプリ外でも確認 | 架空の便や通知を、現在の実データのように見せない |
| TeleDeck | iPadの操作パネルとMac側の画面 | パネルを選ぶ→操作が届く→Macが変わる | サイト上で実際のMacを操作できるように誤解させない |
| Tsumugi | 記事保存・要約・診断の実画面 | 保存→要点→診断根拠 | 診断の数値や効果を、根拠なしに新しく作らない |

字幕と主CTAは動く画面の外に置く。説明中のどの位置でも「詳しく」を押せるようにする。素材が足りない場合は静止画＋注釈から始め、連番画像を大量生成して埋めない。

## 7. アプリ一覧のhoverプレビュー

参照G06、H27。現在のカードtiltと役割が重なりやすいので、一つのカードに追従・tilt・全体引力を全部かけない。

推奨は、一覧の右側またはカードの余白に、小さい実画面を表示する方式。ポインターに追従するのは画像だけで、タイトル・説明・クリック面はその場に残る。

- 最初はSubghost・BusTimeApp・Tsumugi等、素材のある主要作品に限定。
- pointerenterで対応画像を表示、pointermoveで枠内にclamp、pointerleaveで消す。
- 150〜250ms程度の短い表示と、少し遅れる座標追従を比較する。読みたい文章を隠さない。
- 高速に隣のカードへ移ったときに、古い画像が後から出ないよう選択とdecodeの結果を照合する。
- Tabでフォーカスした場合は、追従せず所定位置に同じ画像を出せる。Escapeで不要な面を閉じられること。
- スマホでは通常のサムネイルを使う。最初のタップでhoverだけ、二度目で遷移という操作にしない。
- `Projects.tsx`の既存`data-motion-work`を整理し、追従対象のカードでは大きいtiltを止める。

## 8. 大きい制作過程のシーン

これは第二段階。参照の荷役→運送のような「何がどう変わったか」を、RHの仕事に置き換える。

```text
短いアイデアのメモ
  → ワイヤーフレーム
  → デザインされたアプリ画面
  → 実装・テストの一場面
  → 実際に動くアプリと、そのソースへのリンク
```

おすすめの場所はSkillsとAppsの間、またはApps内の「開発の軌跡」の導入。両方には置かない。

描画方式は、最初はHTML／SVG／実画面の重なりを使う。カメラが複雑に回る必要が明確になった場合だけ連番やThree.jsを比較する。制作過程は事実に基づく素材を用意し、説明のための架空コードや架空テスト数を実績として使わない。

## 9. 全体に効く小さい反応

| 要素 | 採用案 | 既存実装との調整 |
| --- | --- | --- |
| 主CTA | 斜め矢印が抜けて次の矢印へつながる | magneticは弱く。ボタンのhit areaは固定 |
| セクションリンク | 二重文字の短いroll、下線の走り抜け | キーボード選択時は即時の色・outlineを使う |
| 技術名や短い英語ラベル | 必要な一部だけ文字シャッフル | 日本語の長文・フォーム・現在値には使わない |
| 連絡CTA | 複数の円がゆっくり拡がる | メールアドレスと送信ボタンの背後に強い動きを置かない |
| 実績の数値 | 初回だけカウントする | 読み上げには最終値を渡し、スクロールごとに0へ戻さない |
| 背景の点 | マウス速度に反応する小さい尾 | 速度計の装飾として扱う。文字の可読性・入力の邪魔をしない |

UI全体の新しいCSS変数を増やす前に、既存の`--site-ease`、色、radiusを使う。オレンジ・青の新ロゴは署名・ロゴに集約し、本文の強調色を無差別にグラデーションへ変えない。

## 10. ページ遷移の整理

今ある`ProductMorph`を第一候補として完成させる。参照の円形カバーをすべての移動へ追加すると、同じ移動にshared imageと円とrevealが重なる。

| 操作 | 推奨する反応 |
| --- | --- |
| アプリカード→詳細 | 画像・タイトル・面のshared transition。対象が見えない場合は短いfallback |
| Heroのアプリ→詳細 | アイコンの受け渡しを比較。Hero→Showcaseのscrubとは別の遷移として管理 |
| メニュー→同ページの章 | 短い移動または即時移動。毎回大きい画面wipeを再生しない |
| ⌘K・キーボード移動 | 機能上の選択と移動を優先。decorativeな待ちを入れない |
| 次のプロダクト | 一貫した一種類の反応。行き先ごとに別の効果を乱立させない |
| 初回の導入 | 既存の円形openを使える。戻る・再訪では繰り返さない |

共通のキャンセルとcleanupを持ち、連打・戻る・遅い画像・JavaScript例外で画面のoverlayが残らないことを確認する。

## 11. 実装・検証の順序

## 13. 追加の実画面観測を踏まえた設計の補強

### 描画に失敗しても署名は残す

ChromeシークレットとBraveの新規タブでは、フッターの情報は読めた一方、点描文字の位置は空白だった。BraveのコンソールにはGSAPの`refresh`で`undefined.end`を読む例外もあった。空白との直接の因果関係は未特定だが、RHでは重い演出の成功を普通の情報表示の条件にしない。

`ParticleWordmark`は、準備中・利用可能・失敗を分ける。HTMLの名前を最初から表示し、**最初のcanvas描画成功後**に表示を交換する。画像decode、font待ち、canvas取得、resize再生成のどこで失敗しても静止した名前を復帰させる。Heroから離れた場所にあるFooterを、Heroの重い初期化の成否に依存させない。

### 被写体を動かす区間と、読む停止位置を分ける

参照の飛行機はスクロール前後で位置が変わり、巨大な前景としてコメントに重なる状態も見えた。RHで同じ迫力を狙うなら、拡大するアプリ画面の通り道に本文を置かず、画面が収まった位置に説明を続ける。

比較では「スクロールを止めた任意の位置で、何が読めて何が押せるか」を確認する。途中で止める、途中からアンカーで入る、逆に戻る、短いviewportで見る、の4条件を含める。終点のスクリーンショット一枚だけで完成にしない。

### CTA円は補助にする

参照では広い黒いCTAの上に、オレンジの`WORK WITH US`円がpointer位置で見え、フッターへ進むと通常のringへ戻った。RHではContactの余白で同系統の反応を比較できるが、移動する円だけを唯一のリンクにしない。固定したEmail・GitHub・問い合わせの操作を残す。

### 最初のloaderに必要な情報を選ぶ

参照loaderでは国名・サービス・地図・進捗が一つの画面に集まっていた。RH側の既存地図を磨く場合も、単に地図を精細化するより、`iOS / macOS`、実在のアプリ名、本人の名前など、入口で伝えたい情報との接続を比較する。loaderのために新しい待ち時間は追加しない。
