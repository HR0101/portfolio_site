# スクロールを止めても動く表現の参考集

調査日：2026-11-09（JST）

関連：[Hero以降を引き上げるポートフォリオ調査](./portfolio-inspiration-research-2026-11-09.md)

目的：Heroの自転する惑星のように、訪問者が何も操作していない間にも見どころがある表現を集める。今回は参考資料と応用案の整理まで。サイトへの追加実装は行っていない。

## 1. RHで最初に試したいもの

**常時動くものを加える方向は合っている。ただし、各章で「何が動いているのか」が作品や本人の活動につながっていると、Hero以降にも個性が生まれる。** これは下記の資料を踏まえたRH向けの設計判断。

| 優先 | 場所 | 操作していない間に見えるもの | 狙い |
| --- | --- | --- | --- |
| 1 | Skills | 入力が届き、状態が変わり、ネイティブUIが完成する小さな制作工程 | 技術名を、実装の働きとして見せる |
| 2 | EkiHub | 複数の出発点から点が路線を進み、集合候補駅へ集まる | サービスの目的を数秒で理解させる |
| 3 | Tsumugi | 小さな情報片が編まれ、整理されたカードになる | 名前と機能を同じ動きで表現する |
| 4 | About | 本人の制作物の横で、点・セル・模様の小さな実験が進む | 「作り続けている人」という印象をつくる |
| 5 | 代表アプリ | 実際のアプリ操作の短い映像が、静止時間を挟んで繰り返す | スクリーンショットから使用感まで見せる |
| 6 | 章の境界・展示の余白 | 白黒の点の波や、布のような面がゆっくり変化する | 文章を邪魔せず、ページの空気をつなぐ |

一つの画面内では、強く動く主役を一つに絞る。Heroの惑星、Skillsの工程、作品内のデモと、スクロールで主役を受け渡す。全カードを同時に浮遊させる案は優先しない。

## 2. 確認範囲と読み方

- **20例を収録。20の異なるポートフォリオではなく、作者の実験、公式デモ、同一ライブラリの異なる表現を含む。** ポートフォリオ本体の構成は前回資料を参照。
- 時間・反復処理・シミュレーションで進むものを対象とした。スクロール、ホバー、マウス移動だけを動力にするものは分けた。
- **A＝公式コードまたは公式仕様で時間更新／反復を確認。B＝作者による動作説明を確認。** 見た目の優劣や完成度の採点ではない。
- 今回はブラウザ操作ホストに接続できず、デモをライブ画面で再生・操作して確認していない。公開本文・公式ソース・作者解説による調査。実機の滑らかさ、開始操作の有無、最新ブラウザでの動作は未検証。
- 「デモ」はデモページへのリンク。「資料内」は記事や公式ドキュメントに埋め込まれた例。ページによって読み込みや開始操作が必要な可能性がある。
- 後半の秒数・振幅・配置は**RHへの提案値**。参考ページから測定した値ではない。
- 各例の「応用」は本資料の提案であり、参考サイトに存在する機能の説明ではない。

ここでいう「常時」は、**その展示が画面内にあり、訪問者が停止していない間に進む**という意味。画面外や非表示タブでも動かし続ける設計にはしない。

## 4. RH向けの具体案

以下は参考表現をRHの作品に翻訳した新しい案。チェックは実装状況を表す。既存の小さな点滅・パケット表現だけで完了とはしない。

### I01：Skillsに「動いている小さな制作工程」

- [ ] 未実装
- 参考：L19の連動、L03の時間更新。表示内容は実際のSwift／SwiftUI作品に由来させる。
- **何もしなくても**：入力が一つ届く → 状態の図が変わる → アプリの一部が更新される → 完成状態をしばらく見せる。
- 例：BusTimeAppのサンプル停留所 → 次の便の判定 → 出発までの表示。実際の仕様を調べてから内容を決める。
- 1周8〜12秒の提案。4〜6秒は完成状態を保ち、リセットは図の外への退場や短い切替でつなぐ。
- 見出し・技術名・説明文は固定。工程の図とUIの局所だけを動かす。
- 操作を始めたら自動進行を止め、選んだ状態を維持する。自動再生の再開を選べるようにする。
- 候補技術：SVG／DOM＋CSSまたはWAAPI。複雑な3Dより先に、実UIの完成度を揃える。
- **既存との差**：小さな通信点の反復ではなく、入力と結果の関係が一目で分かる展示にする。

### I02：EkiHubの「人が集まる路線図」

- [ ] 未実装
- 参考：L19の連動する部品。線と点への置換、集合候補の説明はRH向けの応用。
- **何もしなくても**：3つ程度の出発点から小さな点が進む → 候補駅へ集まる → 候補を短く強調する → 次の例へ。
- 1周10〜14秒の提案。路線・駅名・候補の説明は読める時間を確保する。
- 実データのサンプルか、説明用に単純化した例かを明示する。ライブの利用者位置に見せない。
- 既存の路線SVGを土台に、動く点と到着状態を加える候補。SVG＋CSS／WAAPIでまず検討する。
- **既存との差**：路線を飾りにせず、「集合場所を決める」機能そのものが動く。

### I03：Tsumugiの「情報を編む動き」

- [ ] トップページの展示としては未実装

## 6. 混同しなかったもの・追加確認が必要なもの

- **Paperの「Waves」は静的パターン。** 名前に波が入っていても、公式仕様は静止した線模様として説明している。今回の20例には含めていない。[公式仕様](https://shaders.paper.design/waves)
- **スクロールで章が切り替わることと、素材が時間で揺れることは別。** L20は布の時間変化を参考にする。ページ全体をスクロール非依存と判定したわけではない。
- **粒子があるだけで常時動くとは限らない。** マウスで崩れる文字、ホバーだけの屈折、カーソル追従は補助の反応として扱う。
- **無限スクロールと無限アニメーションは別。** スクロールし続けないと進まない作品は、今回の主対象にしない。
- **シミュレーションは必ずしも永久に変化しない。** L06のように安定・消滅する仕組みは、反復映像と同じ扱いにしない。
- **WebGL／WebGPUは動力を作る手段。** 時間による更新はCSS、SVG、Canvas、動画でも作れる。写実的な素材や美しい構図が自動的に得られるわけではない。

## 7. 実装するときの共通条件

1. スクロール位置ではなく、経過時間やシミュレーションの状態で進める。画面内判定は再生の開始・停止だけに使う。
2. 短い工程には「結果を読める静止時間」を入れる。継ぎ目を隠すために常に高速で動かさない。
3. 自動で動く展示には停止手段を設ける。`prefers-reduced-motion`では代表フレームや手動再生に切り替える。
4. 画面外・非表示タブでは更新を止める。戻ったときに一気に時間を消化しない。
5. DOMの単純な動きは`transform`／`opacity`を中心にする。毎フレームのReact state更新や、巨大な親要素の継承CSS変数更新を避ける。
6. 粒子数・描画解像度・動画容量を展示サイズに合わせる。シェーダーを使っただけで軽くなるとは判断しない。
7. 本文・リンク・重要な数値は静止させる。アニメーションを止めても、作品と説明が成立する構成にする。
8. まず一つの展示を作り、スマホ実機とSafariを含めて確認する。本調査ではフレームレートや消費電力を計測していない。
